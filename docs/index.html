Virtual IP failover that never claims an address it does not hold, and never makes you guess why.

Highland is a memory-safe Rust implementation of VRRPv3 for Linux: a deterministic state machine, native health checks, transactional configuration reload, and an event stream that explains every single role change. A library first, a daemon second.

01 Honest status

What works today, and what does not

Highland is pre-release, and this page will not say otherwise. A whole failover — election, ownership confirmed by read-back, a takeover announced to the segment, and the address moving — runs in the test suite between two real network namespaces, over IPv4 and IPv6, unicast and multicast, with packet loss, reordering, a one-way partition, a link flap, and a frozen node injected into the segment. What is left is written down, not implied.

Shipped and tested

  • Configuration model, strict TOML parser, and 32 validation rules, each with its own test
  • Deterministic state machine: roles, timers, election, health arithmetic, no runtime dependency
  • VRRPv3 codec for IPv4 and IPv6, RFC 1071 checksums, six fuzz targets in CI
  • Linux netlink backend, raw VRRP sockets, and gratuitous ARP and unsolicited Neighbor Advertisements
  • IPv4 and IPv6, unicast and multicast, each a two-namespace suite
  • Five chaos scenarios: loss, partition, reordering, duplication, link flap, frozen process
  • Control socket, Prometheus metrics, and an event history with a cursor
  • Transactional reload, applied by highland reload or SIGHUP — one path, so the two cannot disagree
  • Native tcp, http, unix, and interface health checks, with thresholds and weighted demotion
  • Interoperability with Keepalived over IPv4 unicast, in both directions, which found a checksum scope the RFC requires and the two implementations disagreed about

Not yet

  • Keepalived interoperability for IPv4 unicast, tested in both directions; IPv6 and multicast are not yet run against a second implementation
  • One instance holding both IPv4 and IPv6 addresses — refused, with a reason, rather than half-supported
  • https, dns, and process health checks, all refused by name at startup
  • Changing a check list without restarting the instance
  • Configurable hold-down and retry, and a --yes confirmation prompt
  • An sd_notify readiness message, so the unit file uses Type=simple
  • Fencing against split brain, which is outside the election path by design

02 What it refuses to do

Three commitments, and they cost something

Ownership before advertisement

A node reads its addresses back from the kernel before it is allowed to announce itself as their owner. Taking ownership is a two-step operation: add, confirm, then advertise. There is no degraded mode in which a node claims an address it does not hold — not even a configurable one. If it cannot take ownership it says which interface, which address, and which kernel error.

Every transition carries a reason

I-04 is structural, not a convention: there is no code path from BACKUP to MASTER and on to an advertisement except through a confirmed add. Ties break in a documented, deterministic order, and a single failed probe cannot move an address — thresholds and a grace period are enforced by the scheduler, not left to the probe.

Honest about split brain

Highland is a layer-2 tool. During a network partition two nodes can both believe they own the address — and a node that is killed, frozen, or partitioned keeps holding it, because nothing can tell it otherwise. The chaos suite asserts that the segment converges once the fault heals, and documents the window in between rather than claiming it away. Fencing is post-1.0 and deliberately outside the election path.

03 Architecture

A library that happens to ship a daemon

Nine focused crates. Dependencies flow strictly downward, cycles are forbidden, and the two crates at the bottom depend on nothing at all — which is what makes the state machine and the protocol codec testable without Linux, without a network, and without an async runtime.

01highland-coreRoles, timers, election, health arithmetic. No Linux, no runtime, no I/O. 02highland-vrrpVRRPv3 encoding, decoding, checksums, validation. No sockets. 03highland-configTyped TOML model, 32 validation rules, source-located errors. 04highland-observeEvents, redaction, bounded history, Prometheus metrics. 05highland-netInterfaces, addresses, netlink, and the receiver-side VRRP rules — behind a trait. 06highland-checksNative probes with thresholds, weights, bounded timeouts. 07highland-controlLocal Unix-socket API. Never a network listener. 08highland-daemonProcess lifecycle, signals, shutdown budget, wiring. 09highland-cli`highland` — mapped exactly onto the control API.

04 Explainability

A closed set of reasons, and you can look them all up

Every role change carries one of these thirteen. The set is closed on purpose: dashboards and alerts depend on the spelling, so a new reason is a specification change, not a surprise release note.

startupThe instance entered election
interface_upThe interface became usable
interface_downThe link went away
master_down_timeoutNo advertisement in 3 × adver_int + Skew_Time
higher_priority_peer_advertisementA peer outranked this node
preemption_delay_elapsedA higher-priority backup took over after its delay
health_ineligibleHealth policy removed eligibility
operator_relinquishAn operator gave the address up
operator_force_transitionAn operator forced the role
configuration_reloadedA reload permitted the transition
hold_down_expiredA fault recovered and re-verified
ownership_failedAn address could not be added or removed
shutdownThe process is stopping
